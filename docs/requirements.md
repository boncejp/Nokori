# Webアプリケーション『Nokori』要件定義書 v2.0

## 1. プロジェクト概要

### 1.1 プロダクトコンセプト

「あといくら使えるか」を1秒で同期する、貯金伴走型Webアプリ。
ユーザーが脳内で行っている「目標からの逆算」と「日々の予算管理」をデジタル化し、精神的余裕（ゆとり）を持ちながら最終目標（貯金）を達成するための意思決定支援ツール。

### 1.2 ターゲットユーザー

明確な貯金目標（例：半年で50万）を持っているが、日々の支出管理にストレスを感じている人。
家計簿アプリの「記録」に挫折し、「今日いくら使っていいか」の直感的なガイドを求めている人。
（※初期リリースは個人利用に特化し、運用検証を行う）

### 1.3 サイクル種別（実装・要件の前提）

本アプリの予算・リセット処理は、**初回サイクル**と**2回目以降の通常サイクル**の2系統を明確に区別する。後続実装では、現在がどちらのフェーズかを判定したうえで、該当するロジックのみを適用する。

| 区分 | 期間の考え方 |
|---|---|
| **初回サイクル** | アプリ利用開始日（オンボーディング完了の論理日）から、**次の給料日の前日**まで。 |
| **通常サイクル（2回目以降）** | 各給料日を起点とした月次サイクル。初回サイクル終了後の最初の給料日リセットから適用。 |

## 2. コアロジック（アルゴリズム）

### 2.1 27:00（AM 3:00）リセットロジック

- **定義:** 1日の区切りをAM 3:00（JST基準）に設定。
- **挙動:** 00:00〜02:59の入力は「前日の支出」として論理日付を前日に設定する。03:00にその日の最終収支を締め、余剰金・不足分を確定させる（**通常サイクル**における日次締めの前提。初回サイクル中の日次表示ロジックとは組み合わせて定義する）。
- **目的:** 深夜帯の活動を自然に反映させ、翌朝目覚めた時に「最新の今日予算」が提示される状態を作る。

### 2.2 初回サイクル：財産の分け方（オンボーディング時点）

初回サイクルでは、ユーザーが申告する**現在の全財産**を次の2つに分けて管理する。

- **次の給料日まで使う予算** … その期間の生活費として日次予算の母数になる。
- **それ以外** … **資産側**の金額として扱い、初回サイクル中の日次予算の増減対象とはしない。

**例:**

- 現在の全財産: 140,000円
- 次の給料日まで使う予算: 50,000円
- 資産側として扱う金額: 90,000円

**内部的な関係（仕様上の不変条件）:**

- `initial_total_assets` = オンボーディング時点の現在の全財産
- `initial_budget` = 次の給料日まで使う予算
- `current_total_savings` = `initial_total_assets` − `initial_budget`（**オンボーディング初回保存時の初期化に限る**）

この等式で `current_total_savings` を求めるのは上記のタイミングだけとする。**設定変更の保存**のたびに `initial_total_assets` と `initial_budget` から再計算して貯金総額を上書きしてはならない。運用中の貯金総額は、初回サイクル締め・特別支出・通常サイクル締めなどの**資産変動ロジック**でのみ更新する。

オンボーディングでは「現在の貯金総額」という単一項目ではなく、**現在の全財産**と**次の給料日まで使う予算**を入力させる。前者だけでは「生活費に回す分」と「資産側」の切り分けが表現できないためである。

### 2.3 初回サイクル中の予算計算

初回サイクル中は、**通常サイクルとは別ロジック**とする。光熱費概算との差額反映は行わない。特別支出は扱わない。

- **初回残り予算** = 次の給料日まで使う予算 −（初回サイクル開始日から**前日**までの**普通支出**合計）
- **当日予算** = 初回残り予算 ÷ 次の給料日までの残り日数（**当日含む**）
- **今日の残り予算** = 当日予算 − 今日の**普通支出**
- **翌日以降予算プレビュー** =（初回残り予算 − 今日の**普通支出**）÷ 明日以降の日数

論理日の切り替え（27:00ルール）は通常サイクルと同じく適用し、集計上の「前日」「当日」「残り日数」は上記の式に合わせて解釈する。

### 2.4 通常サイクル（2回目以降）の動的日次予算

初回サイクル終了後、各給料日を境にしたサイクルでは、従来の可処分予算ベースのロジックを維持する。

**月次貯金ノルマ:**

```
月次貯金ノルマ = (目標金額 - 現在の貯金総額) ÷ 目標日までの残り月数
```

**可処分予算の基準:**

月収 − 固定費 − 光熱費概算（電気・ガス・水道の合計）− 月次貯金ノルマ

**支出種別ごとの反映（通常サイクル）:**

- **普通支出:** **今日の残り予算**（当日予算 − 当日の普通支出合計）から**だけ**減らす。日次予算の「今日」側の消費は普通支出に限定する。
- **光熱費:** 実額と概算の差額を**当月の残り予算**に反映する（実額が概算より安い場合は予算増、高い場合は予算減）。入力の瞬間に**今日の残り予算**から差額を直接減算（または加算）してはならない（当日の減算対象は**普通支出**のみ）。差額は当月残りに織り込まれたうえで、**翌日以降予算プレビュー**に加え、**翌日以降の論理日が始まるたびに再計算される当日予算（`D_today`）**にも反映される。つまり「今日の残り」は普通支出ベースで保ちつつ、翌日以降の日次配分には光熱費差額を含める（設計書 §4.2.2 / §4.3 と整合）。
- **特別支出:** **貯金総額**から直接差し引く。**当日予算・今日の残り・翌日以降の母数**には載せない。発生のたびに**月次貯金ノルマ**を再計算し、以降のサイクル基準を間接的に更新する。

**当日予算・翌日以降（上記を踏まえた式の趣旨）:**

- **当日予算** = 次の給料日までの残り予算 ÷ 次の給料日までの残り日数（当日含む）  
  （残り予算の定義から**特別支出の金額は除外**。ノルマ変更は再計算後の基準に反映。）
- **今日の残り予算** = 当日予算 − 今日の**普通支出**合計
- **翌日以降予算プレビュー** =（次の給料日までの残り予算 + 当月中の光熱費差額の累計 − 今日の**普通支出**合計）÷ 当日を除く残り日数  
  （上記の「光熱費差額の累計」は、翌日以降に回る**当日予算の再計算**にも同じ当月残りを通じて効く。）

**リアルタイム表示・再計算:** 支出登録のたびに「今日の残り」と「翌日以降の予測日次予算」を即時更新する。

**日次締め（27:00）:** 当日の余剰・不足を確定し、翌日の当日予算を正式に決める。

**余剰の等分分配（日次）:** 1日の終わりに余剰金が出た場合、全額を翌日にスライドさせるのではなく、**次の給料日までの残り日数**で等分して翌日以降の予算に分配する。

### 2.5 初回サイクル締め処理（次の給料日リセット時）

初回サイクルが終了し、**次の給料日**にサイクルが切り替わるタイミングでは、**余剰金処理モード（STRICT / YUTORI）を適用しない**。

- **初回差額** = 次の給料日まで使う予算 − 初回サイクル中の**普通支出**合計
- **貯金総額の更新:** `current_total_savings` = `current_total_savings` + 初回差額
- 以降のサイクルは**通常サイクル**として扱う。

**例1（超過）:**

- 資産側 90,000円、次の給料日まで使う予算 50,000円  
- 初回サイクル中の普通支出 60,000円 → 初回差額 −10,000円  
- 次サイクル開始時の `current_total_savings` = 80,000円

**例2（余剰）:**

- 資産側 90,000円、次の給料日まで使う予算 50,000円  
- 初回サイクル中の普通支出 40,000円 → 初回差額 +10,000円  
- 次サイクル開始時の `current_total_savings` = 100,000円

### 2.6 月次サイクル余剰金処理（STRICT / YUTORI）— 2回目以降のみ

**通常サイクル**の給料日リセット時に、サイクル内で余剰金が発生した場合、ユーザーが設定したモードで処理する。

| モード | 余剰金の扱い |
|---|---|
| **STRICT** | 余剰金を全額、貯金総額に追加する。翌月の可処分所得は基準値に戻る。 |
| **YUTORI** | 余剰金を翌月の可処分所得に上乗せする。貯金総額への追加は行わない。上乗せ後の枠は `initial_budget` に保持し、当月中の日次予算の母数（`remainingCycleBudget`）にも同じ値を用いる。 |

初回サイクル締めでは本項を適用しない（2.5 参照）。

### 2.7 貯金ノルマ再計算（通常サイクル）

特別支出等によって貯金総額の変動が発生するたびに、最終目標日までの残り月数で割り、次月以降の「月次貯金ノルマ」を自動再計算する。

```
月次貯金ノルマ = (目標金額 - 現在の貯金総額) ÷ 目標日までの残り月数
```

## 3. 機能要件

### 3.1 認証・初期設定（オンボーディング）

**認証:** Google OAuth / Email 認証（Supabase Auth）。

開発・本番では、**クラウド上の Supabase プロジェクト**において Auth の有効化（Google 等の OAuth プロバイダ）および **Site URL / Redirect URLs** の登録が必要になる。具体的な URL の組み合わせや Google Cloud Console 側の設定は `docs/design.md`（認証・OAuth 運用メモ）に委ねる。

**初期設定フロー（ステップ順）:**

1. 最終目標金額
2. 達成期限（年: 0〜20 / 月: 0〜11 のプルダウン、0年0か月は不可）
3. **現在の全財産**（オンボーディング時点の総額）
4. 月収（手取り概算）
5. 給料日（土日祝の前倒し / 後ろ倒し / 固定 ※日本の祝日判定を含む）
6. 固定費合計
7. 光熱費概算（**電気・ガス・水道を個別に設定**）
8. 余剰金処理モード（STRICT / YUTORI）※初回サイクル締めでは使わないが、2回目以降で使用
9. **次の給料日まで使う予算**（現在の全財産以下であること）

**補足（ユーザー向け説明・ヘルプに含める趣旨）:**

- 初回サイクルでは、現在の全財産から「次の給料日まで使う予算」を切り出し、**生活費**として管理する。
- 残りは**資産側**の金額として扱う。
- 「次の給料日まで使う予算」は「現在の全財産」を超えてはならない（バリデーションで拒否）。

**データ移行:** 過去データのインポートは行わず、新規スタートに特化。既存行がある場合の `initial_total_assets` の導出は設計書（DB）に従う。

### 3.2 ダッシュボード機能

- **メインUI:** 「今日の残り予算」を中央に巨大表示。
- **給料当日の手取り入力:** 論理日付が**通常サイクル**の給料サイクル開始日のとき、ダッシュボードを開いたタイミングで当月の手取り概算を入力するモーダルを表示する（同一サイクルで重複表示しない）。`profiles.monthly_income` を更新し、第2サイクル以降では `initial_budget` を基準予算の増減に合わせて整合させる。初回サイクル中の挙動は実装と設計書で明確化する。
- **クイック入力:** 金額入力 → 決定の最小ステップ。
- **属性選択（ユーザー向けラベル）:** アプリ上の表示・ヘルプでは **「普通支出 / 特別支出 / 光熱費」** とする（内部実装名は設計書に委ねる）。
  - **普通支出:** 当日の日次予算から差し引く。翌日以降の予算を即時再計算する。
  - **特別支出:** 貯金総額から直接差し引く（当日・翌日以降の日次予算の母数には載せない）。入力後、月次貯金ノルマを自動再計算する。**初回サイクル中は登録不可。**
  - **光熱費（電気 / ガス / 水道）:** 実額入力時、各項目の概算との差額を当月残り予算に即時反映する。**初回サイクル中は登録不可（差額計算も行わない）。**
- **初回サイクル中のダッシュボード:** **普通支出のみ**登録可能とする（特別支出・光熱費の入力UIは出さない、または無効化）。
- **初回サイクル中の説明表示（趣旨）:** ダッシュボードに次の内容を表示する。
  - 初回サイクルでは、次の給料日まで使う予算だけを**普通支出**として管理する。
  - **光熱費**と**特別支出**の詳細管理は、次の給料日以降の**通常サイクル**から利用できる。
  - **通常サイクル**では、光熱費は概算との差額を残り予算へ反映し、特別支出は貯金総額から直接差し引いて月次貯金ノルマを再計算する。
- **翌日以降予算プレビュー:** 支出登録のたびにリアルタイム更新される「明日以降の予測日次予算」を表示する（初回・通常で式は異なるが、ユーザー体験は同一の枠組み）。
- **警告表示:** 当日予算超過時、画面全体に赤系統の警告色を適用。

### 3.3 履歴管理機能

- **支出リスト:** 当月の支出を時系列で表示。
- **編集・削除:** スワイプによる削除。削除時は当日予算および翌日以降の予算を即時再計算。

### 3.4 設定・シミュレーション機能

- **動的シミュレーション:** 達成期限や固定費を変更した際、確定前に「今日の日次予算」への影響をリアルタイムにプレビュー（通常サイクルが主対象）。
- **達成期限編集:** 設定画面では達成期限を年/月で編集する。目標日（YYYY-MM-DD）は表示専用とし、給料日または補正ルール変更時に同じ期間指定から自動再計算する。
- **月次貯金ノルマの表示:** 設定画面に**月次貯金ノルマ**を表示する。**編集不可**。**初回サイクル中は非表示**とし、**2回目以降の通常サイクルでのみ表示**する。
- **貯金総額の保全:** 設定の保存（目標・固定費・光熱費概算・給料日等の変更）では、オンボーディング初回保存時に用いた初期化の考え方で**貯金総額を再計算・上書きしない**（運用中に変動した値を巻き戻さない。設計書 §4.8）。
- **データ初期化:** 全データを削除し、初期設定からやり直す機能。

## 4. 非機能要件

### 4.1 UI/UX デザイン

- **ビジュアルテーマ:** Apple風ミニマリズム。
- **カラー:** ネイビー（#001F3F等）とホワイト。
- **タイポグラフィ:** モダンなサンセリフ体（SF Pro / Inter）。
- **アクセシビリティ:** 各スイッチに挙動を説明するスタイリッシュなヘルプテキスト（ツールチップ）を実装。

### 4.2 技術特性

- **Webアプリ (PWA):** ホーム画面追加、基本的なキャッシュによる高速化（オフライン時の完全な入力データDB同期はV2拡張とする）。
- **パフォーマンス:** 楽観的UI更新によるゼロ・レイテンシ体験。

## 5. 画面定義

- **Dashboard:** 今日の残り予算表示、テンキー入力、属性トグル（**通常サイクル:** 普通支出 / 特別支出 / 光熱費。**初回サイクル:** 普通支出のみ）、翌日以降予算プレビュー、初回サイクル用の説明テキスト。
- **History:** 支出一覧、スワイプ削除。
- **Settings:** マスター設定（光熱費概算を電気・ガス・水道で個別設定）、余剰金処理モード選択（STRICT / YUTORI）、**通常サイクル時のみ**月次貯金ノルマ（表示のみ）、「次の給料日まで使う予算」は**初回サイクル中のみ**入力可（通常サイクルでは非表示・設定 PATCH でも上書きしない）、YUTORI 時は前月からの繰り越し参考表示、期間シミュレーション、データ初期化。

## 6. 技術スタック
